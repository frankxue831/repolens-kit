## Purpose

This document exists because of a concrete failure mode: describing the product's **destination** as if it were its **current behaviour**. The arc of work from commit `3d20aef` through `2a6ba74` built a lot of philosophy and infrastructure, and it is tempting to narrate RepoLens in terms of what the philosophy promises. Narration like that is not just imprecise — it is the same class of ungrounded observation that doc 06 §7 exists to prevent. Future readers and future narrators (human or agent) should reference this table before describing what the product "does."

The rule: **when describing RepoLens to an agent or a human, quote from the "Shipped today" column. Use the "Direction of travel" column only when explicitly discussing roadmap.** Do not blur the two.

## Known Mismatches Between Narration and Reality

A reviewer-identified set of claims that sound true because of the philosophy but are **not true of the current code**. Preserved here as evidence that narration can drift:

1. **"`get_summary` returns grounded memories."** Partly true as of the Phase 3 rollout of the 2026-04-18 get_summary memory population plan, which implements Option A (narrow) from the [2026-04-18 scope design](../superpowers/specs/2026-04-18-get-summary-scope-design.md). Shipped behavior: `SummaryService::summarize` loads the memory graph when a `repo_root` is supplied, runs the same lazy-decay step `recall_longterm` uses, and populates `memory_insights` via a tier-dependent selection rule — **compact: 3 insights**, **standard: 5**, **full: up to 20** — with per-item `groundingStatus` (`Confirmed` / `Contradicted` / `Unverifiable` / `Unchecked`) reused from `crates/repolens-app/src/grounding.rs`. Compact and standard tiers filter to memories with at least one anchor that resolves against the current pack; full tier applies a 1.5x importance bonus to resolving anchors but does not filter. Updated 2026-05-24: as of Phase 4B Step 4 (2026-05-13), the `get_summary` envelope emits `derived` by default but **falls back to `unaudited` when `memoryInsights` is non-empty**, because memory-store content is not doc-06 §5 graded and cannot be implicitly promoted (see `min_envelope_grade` and the `has_memory` gate in `crates/repolens-mcp/src/tools/summary.rs`). The grade is therefore state-dependent, not statically `unaudited`. Catalogue coverage for memory-insight payloads (or per-field envelope grades) would let it stay `derived` with memories present.

2. **"`get_impact` is verified."** False. Demoted to `derived` in commit `071aa25` after the first review found that BFS blast-radius traversals have no invariant coverage on their output.

3. **"`Confirmed` memories decay slower."** **Shipped** as of 2026-05-29 (on recall) and extended 2026-05-31 (on scan + get_summary). `recall_longterm`, `repolens scan`, and `get_summary` all now write the grounding assessment as `MemoryNode.last_grounding`, and the decay engine consumes it: `Confirmed` raises the importance floor (slower decay), `Contradicted` applies a multiplier (faster decay) — see row 26 above. The snapshot now refreshes on scan / get_summary / recall (no longer recall-only); a memory never scanned-against nor surfaced/recalled still carries `last_grounding = None` (neutral decay). This is field-based, not edge-based; the older note still holds that `Contradicts` *edges* (memory → memory — see row 23) are a separate, stronger, status-independent signal.

4. **"`memorize_insight` automatically pins memories to anchors."** False. Anchors are an optional input. A caller that does not supply anchors gets a memory that will return `Unchecked` at every recall.

5. **"Every invariant failure drops the trust level."** Too strong. The lockstep maintenance rule is a governance contract reviewers follow. Nothing in CI or the test harness demotes `evidenceGrade` when a test goes red.

6. **"The envelope is `{ knowledgeLayer: "observation", ... }`."** Simplified. `KnowledgeLayerField` and `ProvenanceField` are untagged enums that serialize as either a single value or an array. Narration should say "single value or array" or show both forms.

## Where the Evidence Lives

When you want to verify a claim about current behaviour, read these first:

- **Envelope types and helpers**: `crates/repolens-core/src/model/epistemic.rs` (canonical; `crates/repolens-mcp/src/epistemic.rs` re-exports and keeps the `ok_epistemic`/`ok_epistemic_graded` helpers)
- **Tool promotion grades**: grep `ok_epistemic_graded\|EvidenceGrade::` across `crates/repolens-mcp/src/`
- **Grounding logic**: `crates/repolens-app/src/grounding.rs` (assessment + `record_grounding` snapshot write-back)
- **Memory decay logic**: `crates/repolens-memory/src/decay.rs` (consumes `MemoryNode.last_grounding`: `Confirmed` floor, `Contradicted` multiplier)
- **Evidence-aware findings**: `crates/repolens-core/src/model/evidence.rs` (data model + `metric_names::ALL`), `crates/repolens-app/src/evidence_findings/` (health findings; `mod.rs` builder + one file per family), `crates/repolens-app/src/compare_findings.rs` (delta findings), `crates/repolens-mcp/src/triage.rs` (`triageHeader`/`notChecked`/`calibration`), `crates/repolens-profile/src/repo_context.rs` + `crates/repolens-profile/src/lockfile.rs` (repo-shape tags + Cargo.lock state), `crates/repolens-core/src/path_classification.rs` (shared root/policy filter)
- **Catalogue coverage**: `docs/philosophy/06-observation-invariants-and-grounding-eligibility.md` §5 table (row-by-row, each row is citation-accurate about which invariants back it)
- **Philosophy vs implementation boundary**: `docs/philosophy/04-current-boundaries.md` (exists specifically to document this distinction for the *observation/interpretation* split; this doc extends the same discipline to the *shipped/aspirational* split)

## Using This Doc

When you are about to describe what RepoLens does — to an agent, in a commit message, in a README, in a spec — first read the "Shipped today" column above. If the description you are about to give mentions behaviour that the column does not list, either:

1. Verify it against the current code and update this table if you find new shipped behaviour; or
2. Rephrase the description to explicitly say "direction" / "future" / "roadmap"; or
3. Remove it.

This document is a **governance tool for narration**, not a marketing page. Keep it boring, current, and citation-accurate.
